# Interaction cost: reducing clicks, effort and friction — full rule set

Sources: The UI/UX Playbook (uxpeak; IDs A-… to H-…, page numbers are PDF pages) and, for W-… IDs, paraphrased tips from public UX pattern pages (cited as web:<slug>, no page; label findings `source: web`). Kind: check (yields findings), default (a value to build with), principle (background, never a finding). Generated by scripts/build-knowledge.mjs — do not edit by hand.

## Interaction cost: definition (p.98-99)

### F-20 Minimise interaction cost (mental + physical + time effort)  (p.98)
- **Rule**: Interaction cost = the mental, physical and time effort a user must invest to reach their goal with a UI. A well-designed site/app reduces it. Ideal = zero (users find what they want immediately) but usually unfeasible because of feature breadth: aim to reduce cost, not necessarily eliminate it. Diagram: green straight arrow User → Goal (ideal) vs pink zig-zag path with many detours (high interaction cost).
- **Why**: Every unit of effort is friction between the user and their goal.
- **Do / Don't**: Do give the shortest, most direct path. Don't force detours (zig-zag).
- **Audit check**: For each key task, count clicks/keystrokes/scrolls/page loads/decisions and compare with the minimum possible. Don't expect zero; rank findings so the highest-frequency tasks with the highest effort (the biggest detours) come first.
- **Restyle fix**: Apply strategies F-24 to F-30.
- **Also cited as**: F-23 (p.98)
- **Kind**: principle
- **Severity**: medium ; **Tags**: interaction-cost

### F-21 Know the three cost components: cognitive, physical, time  (p.98)
- **Rule**: (1) Cognitive effort: mental processing needed to navigate; complex/unintuitive UI → high load; simple/intuitive → low. (2) Physical effort: number of clicks or keystrokes, amount of scrolling, etc. (3) Time effort: duration to reach the goal; slow loading, complex navigation, task complexity, lack of instructions raise it.
- **Why**: Gives audit lens for classifying friction.
- **Do / Don't**: n/a (conceptual; diagram only).
- **Audit check**: Classify each friction point under cognitive / physical / time.
- **Restyle fix**: Pick fix per component (simplify, shorten path, speed up/add instructions).
- **Kind**: principle
- **Severity**: medium ; **Tags**: interaction-cost

### F-22 Minimise these measurable effort items  (p.99)
- **Rule**: Reduce the amount of: reading, scrolling, searching for useful information, understanding presented information, clicking/touching (without errors), typing, waiting for pages to load, and remembering information to complete a task. (Illustrated with a 15-icon grid of touch gestures — tap, swipe, drag, hold, multi-finger — from visual, decorative.)
- **Why**: These are the concrete sources of interaction cost.
- **Do / Don't**: n/a.
- **Audit check**: Checklist for a flow: long reading before action? long scroll to reach CTA? search needed? many taps/typing? loading waits? info that must be remembered across steps?
- **Restyle fix**: Cut copy, surface info, shorten forms, add autofill, speed up loads, keep context visible.
- **Severity**: medium ; **Tags**: interaction-cost

## Interaction cost: effective strategies (p.100-106)

### F-24 Keep related actions close (Fitts's Law)  (p.100, reaffirmed p.108)
- **Rule**: Closer and larger targets are faster to click. Position actions near the elements they relate to and give them a sufficient clickable area.
- **Why**: Fitts's Law — shorter distance and bigger target = less physical effort/time.
- **Do / Don't**: Do (Spotify, from visual): playback controls (shuffle, previous, play/pause, next, repeat + progress bar) in a persistent fixed bar at the bottom of the screen, highlighted in the screenshot, so users don't navigate to another screen/menu. Don't put the action far from its subject or behind a separate screen. Product page (p.108): good, "Add to cart" pill immediately right of the quantity stepper, below the colour swatches; bad, "Add to cart" at the far right edge, separated from the dropdowns.
- **Audit check**: Distance between an action and the object it acts on; tiny hit areas (touch targets small); controls that require navigating away; a submit CTA far from the inputs it commits (far-right, detached, in another container or column).
- **Restyle fix**: Move controls adjacent to / persistently anchored with their target; enlarge hit areas. Place a submit CTA adjacent to (right of or directly below) the final input it commits.
- **Also cited as**: F-34 (p.108)
- **Severity**: medium ; **Tags**: interaction-cost, buttons

### F-25 Minimise choice (Hick's Law) and curate recommendations  (p.101)
- **Rule**: Decision time rises with the number and complexity of choices. Reduce options; highlight a smaller set of recommended/popular items.
- **Why**: Hick's Law — fewer choices → faster decisions.
- **Do / Don't**: Do (Uber Eats, from visual): curated horizontal carousels "Popular near you" and "New on Uber Eats" (4 cards each visible, "See all" links) instead of a list of hundreds of restaurants; filters (sort, price range, dietary) in a left sidebar. Don't dump hundreds of items/menu entries at once.
- **Audit check**: Count of equal-weight options presented at once (nav items, cards, menu items, filters); is there a recommended/popular/curated subset? For single-choice answer lists (onboarding, survey, filter ranges), are the options finer than the product uses the answer for, e.g. six one-hour sleep ranges where four bands drive the same outcome (inference)? Do adjacent ranges share a boundary ("6 to 7", "7 to 8"), so a value fits two options (inference)?
- **Restyle fix**: Group into curated sets, show top N with "See all", progressively disclose the rest. Merge answer options to the granularity the result is used at and write ranges that neither overlap nor leave gaps ("Under 6 h", "6 h to under 7.5 h", "7.5 to 9 h", "Over 9 h") (inference).
- **Severity**: medium ; **Tags**: interaction-cost, hierarchy

### F-26 Use working memory well: chunk information into ≈7 (±2) manageable groups  (p.101-102)
- **Rule**: People hold about seven items (give or take a couple) in working memory (George Miller). Organise information into meaningful, manageable chunks with clear headings.
- **Why**: Chunking reduces memory load.
- **Do / Don't**: Do (Airbnb listing, from visual): page split into separate boxed chunks — host summary ("Entire home hosted by… 10 guests · 4 bedrooms · 5 beds · 4 bathrooms"), highlights (Dedicated workspace, Unwind in the hot tub), description with "Show more", and "What this place offers" amenities grid with "Show all 21 amenities" — plus a sticky booking card (price £1,597/night, dates, guests, Reserve button, fee breakdown). Don't present a wall of text about the rental.
- **Audit check**: Long undivided text blocks; lists/menus/nav with >~7 ungrouped items; missing section headings; cards or panels whose full description is shown when a short summary would let users scan (inference).
- **Restyle fix**: Add headings, split into groups of ≲7, use "Show more"/"Show all N" to truncate long lists; clamp secondary descriptions to a few lines with a "Read more" toggle that expands in place (inference). Don't truncate text users need to decide (price, terms, errors).
- **Severity**: medium ; **Tags**: interaction-cost, layout

### F-27 Reduce distractions  (p.103)
- **Rule**: Remove attention-diverting elements — animated banners, pop-ups, unnecessary visuals — from task and reading flows. Keep only content and essential navigation.
- **Why**: Distractions pull users away from completing tasks and raise interaction cost.
- **Do / Don't**: Do (Medium article page, from visual): clean minimal layout, one narrow centred column, big bold title, author line, small action row (clap/comment/save/play/share), hero image, body text; top bar only search/Write/notifications/avatar; no pop-ups/ads. Don't add banners, pop-ups, ads.
- **Audit check**: Auto-playing/animated banners, modals on load, ads, decorative imagery competing with main content in task screens.
- **Restyle fix**: Remove or defer pop-ups/banners; strip non-essential visuals and nav on focus pages.
- **Scope**: Ads and promos inside a task flow are H-03; this rule covers other distractions (animated banners, modals on load, reading flows).
- **Severity**: medium ; **Tags**: interaction-cost, layout

### F-28 Promote recognition over recall  (p.104)
- **Rule**: Let users recognise actions rather than recall from memory: use common symbols, icons, phrases and a logical layout; show remembered state such as progress.
- **Why**: Reduces mental effort, frustration and time.
- **Do / Don't**: Do (Disney+, from visual): a "Continue Watching" row at the top (highlighted yellow box) with progress bars under the thumbnails, remembering the episode/timestamp, followed by rows "What to Watch Tonight", "Recommended For You", "Action and Adventure". Don't make users remember which episode/timestamp they were at.
- **Audit check**: Does the UI make users remember info from earlier screens/sessions? Are icons unlabeled/unconventional? Is last-state/progress/recent items surfaced?
- **Restyle fix**: Add "recent/continue" shortcuts, visible state/progress, conventional icons with labels, recently used items.
- **Severity**: medium ; **Tags**: interaction-cost, navigation

### F-29 Streamline tasks: remove or combine steps (autofill)  (p.105)
- **Rule**: Visualise the total number of steps in a process; remove or combine those that don't affect the outcome. Autofill address/credit-card details already entered.
- **Why**: Fewer steps lower physical interaction cost and raise efficiency.
- **Do / Don't**: Do (from visual): mobile checkout (Checkout → Add shipping address → Shipping address form → address field with typeahead suggestions e.g. "354 Oyster Point" → pick suggestion) — address autocomplete suggests full addresses; saved payment ("Pay with Visa •••• 4242") pre-filled. Don't make users retype saved data or go through avoidable steps.
- **Audit check**: Map steps in key flows (checkout, signup); count fields/screens; are there autofill (`autocomplete` attributes), address lookup, saved payment methods, combinable steps?
- **Restyle fix**: Merge/remove steps, enable autocomplete/address lookup, prefill known data.
- **Severity**: medium ; **Tags**: interaction-cost, forms

### F-30 Reduce repetition: automate or batch repetitive tasks  (p.106)
- **Rule**: Automate repetitive tasks or make them easier (bulk actions); reduces physical and cognitive costs.
- **Why**: Repetition multiplies effort.
- **Do / Don't**: Do (Google Sheets, from visual): fill-drag a formula/value across a selected range (cells A1:A17 selected) so one action applies to many cells. Don't force one-by-one edits.
- **Audit check**: Tasks users repeat per item (per row, per product) without bulk select/apply-to-all/duplicate/templates.
- **Restyle fix**: Add multi-select + bulk actions, copy/duplicate, templates, defaults, remember previous choices.
- **Severity**: medium ; **Tags**: interaction-cost, tables

## Interaction cost: worked example — product page (p.107-108)

### F-31 Don't hide options in dropdowns; show them (principle of visibility)  (p.107-108)
- **Rule**: Choices hidden in dropdowns or nested menus may not be known to exist, causing missed opportunities and frustration. Show all options upfront (e.g. colour swatches) so users see choices immediately and can try several before deciding.
- **Why**: Reduces mental effort and clicks. Baseline cost: dropdown colour = 2 clicks + scroll, quantity dropdown = 2 more clicks + scroll, then mouse move + click on "Add to cart" → adding two red chairs costs five clicks, one scroll and a short mouse movement. Improved: changing colour = 1 click + short mouse move.
- **Do / Don't**: Bad ("Ergobliss chair", $199 USD): "Colour" dropdown showing "Green ⌄" and "Quantity" dropdown "1 ⌄", with "Add to cart" (red pill) placed far right. Good: three visible colour options (selected lime-green with ring, plus mustard and salmon swatches) — no dropdown.
- **Audit check**: `<select>`/dropdown used for a small set of options (≈ ≤5-6 options (inference)) that could be shown inline; count clicks to configure and buy.
- **Restyle fix**: Replace dropdown with inline swatches / segmented control / radio chips.
- **Severity**: medium ; **Tags**: interaction-cost, forms

### F-32 Replace text labels with visual samples (visual differentiation)  (p.108)
- **Rule**: Show actual colour swatches instead of colour names as text; colour used as a visual cue is quickly understood.
- **Why**: Faster recognition than reading text.
- **Do / Don't**: Do circular colour swatches (selected one outlined with ring). Don't list "Green" as plain text in a dropdown.
- **Audit check**: Colour/material/pattern/size-image options presented as text only.
- **Restyle fix**: Use swatch chips (with selected state ring) for colour/visual attributes.
- **Severity**: medium ; **Tags**: interaction-cost, forms

### F-33 Use a quantity stepper (− / number / +) instead of a dropdown  (p.108)
- **Rule**: Provide a selector where users click a plus sign or type the number directly, making small changes faster and easier. (Selector shown as bordered box: "−  1  +".)
- **Why**: Fewer clicks and no scroll vs dropdown.
- **Do / Don't**: Do stepper with minus, editable number and plus. Don't quantity dropdown "1 ⌄".
- **Audit check**: Quantity implemented as `<select>`; stepper missing direct numeric entry.
- **Restyle fix**: Replace with stepper (−/+ buttons + editable input).
- **Severity**: medium ; **Tags**: interaction-cost, forms

## Minimizing interaction cost: one-click ordering (p.109)

### G-01 Offer a primary "Buy now" (one-click order) button on product pages  (p.109)
- **Rule**: Reduce the steps between intent and purchase. Traditional shopping needs add to cart → checkout → enter shipping and payment details → confirm. One-Click Ordering lets users buy with a single click, skipping the checkout routine by using stored shipping and payment data. Add a primary "Buy now" button next to "Add to cart". Which of the two is the visually primary one depends on the business model and the UI's goals.
- **Why**: It sharply cuts the cognitive, physical and time effort (interaction cost) needed to place an order.
- **Do / Don't**: Do (shown): the Ergobliss chair product page ($199 USD) has a colour swatch selector (3 swatches, selected one ringed), a quantity stepper (− 1 +), and two pill buttons side by side. "Add to cart" is the outline/secondary style (pink outline, white fill). "Buy now" is the solid filled pink primary. No explicit bad example, but the implied bad case is a flow that forces cart → checkout → forms for every purchase.
- **Audit check**: On product or purchase screens, can a returning user with stored data complete the order in one click? Is there a one-step purchase CTA? Is the primary/secondary hierarchy between "Buy now" and "Add to cart" clear (filled vs outline) and a deliberate choice?
- **Restyle fix**: Add a filled primary "Buy now" button beside an outlined "Add to cart". Back it with saved address and payment. Keep one filled primary per decision area.
- **Severity**: medium ; **Tags**: interaction-cost, buttons

## Web patterns: Motion

### W1-03 Respond to taps within 100ms  (src: animation-timing)
- **Rule**: Taps and presses need a visible response in less than 100ms; a slower reaction feels laggy even when the underlying action completes instantly.
- **Why**: Late acknowledgement makes the interface seem unresponsive.
- **Do / Don't**: Do make `:active`/press transitions brief. Don't let sluggish transitions hold back pressed states.
- **Audit check**: Check `:active`, `active:` and button `transition-duration` values; flag > 100ms on press feedback.
- **Restyle fix**: Set press/active state transitions to ≤100ms (e.g. `duration-75`).
- **Severity**: medium ; **Tags**: motion, interaction-cost

## Web patterns: Feedback

### W1-96 Acknowledge every interaction within 400ms  (src: doherty-threshold)
- **Rule**: Aim to respond inside the Doherty Threshold of 400ms: below 200ms feels instant, 200–400ms is acceptable, above 400ms damages engagement. Perceived speed beats raw speed.
- **Why**: Slow replies make users mentally check out.
- **Do / Don't**: Do acknowledge every interaction within 400ms. Don't hold all visual response until the server answers.
- **Audit check**: Check async actions for immediate loading/pressed state; look for await before any UI update.
- **Restyle fix**: Add immediate acknowledgment: a pressed or pending state on the control at once (W1-03, W1-95); a spinner or skeleton only once the wait passes ~300ms (W2-62).
- **Scope**: Acknowledge on the control itself within 100ms (W1-03) with a pending state (W1-95); show a spinner or skeleton only once the wait passes about 300ms (W2-62).
- **Severity**: medium ; **Tags**: states, interaction-cost

### W1-97 Use skeletons, optimistic updates and progress for waits  (src: doherty-threshold)
- **Rule**: Never leave a screen blank while it loads: show placeholder skeleton shapes once the wait passes ~300ms (W2-62), update optimistically when success is near-certain, and use spinners, progress or inline status for waits beyond the threshold.
- **Why**: Unavoidable waits still feel responsive.
- **Do / Don't**: Do display skeletons and progress. Don't leave the screen empty or frozen while data loads.
- **Audit check**: grep loading branches returning `null` or blank; check for `Skeleton`/`animate-pulse` and progress components.
- **Restyle fix**: Add skeleton placeholders and progress indicators.
- **Scope**: Show the loader only once the wait passes about 300ms (W2-62).
- **Severity**: medium ; **Tags**: states, interaction-cost

### W2-62 Show no loading indicator under ~300ms  (src: loading-states-system)
- **Rule**: When a response lands in under ~300ms, show no loading state at all.
- **Why**: A flash of a loader looks like a glitch more than feedback.
- **Do / Don't**: Do delay showing loaders (~300ms). Don't flash a spinner or skeleton for fast responses.
- **Audit check**: Check loading flags are set immediately (`setLoading(true)`) without a delay/minimum threshold; look for flicker in fast fetches. Never mix spinners and skeletons in one view.
- **Restyle fix**: Add a ~300ms delay before showing the loader (and optionally a minimum display time).
- **Also cited as**: W3-51 (web:skeleton-loading)
- **Severity**: low ; **Tags**: states, motion

### W2-64 Don't use optimistic UI for payments or irreversible actions  (src: optimistic-ui)
- **Rule**: Keep optimistic updates for reversible, low-stakes actions. Charges, bookings, and confirmations should appear only after the server approves them.
- **Why**: Falsely reporting success on irreversible actions is expensive.
- **Do / Don't**: Do wait for server approval on payments and transfers. Don't show a confirmation ahead of clearance.
- **Audit check**: grep optimistic updates in payment, transfer, or booking flows. When optimistic UI is used, repaint with the server's result once it arrives. For cheap, reversible actions update the UI at once and roll back visibly on failure.
- **Restyle fix**: Replace optimistic confirmation with a real pending state until the server confirms.
- **Also cited as**: W1-38 (web:behind-the-button); W2-63 (web:optimistic-ui)
- **Severity**: high ; **Tags**: states, interaction-cost

## Web patterns: Navigation

### W2-72 Keep primary navigation out of the hamburger menu  (src: navigation-patterns)
- **Rule**: Hamburgers suit secondary links; hiding primary ones there cuts engagement ~40% on mobile and ~56% on desktop. A command palette (Cmd K) only accelerates, so keep visible navigation too.
- **Why**: Few people use hidden navigation, and newcomers never find shortcuts.
- **Do / Don't**: Do keep primary destinations visible. Don't make a hamburger or command palette the sole route.
- **Audit check**: grep hamburger/menu-toggle components wrapping primary links at desktop widths; check features reachable only via a command palette.
- **Restyle fix**: Surface primary links in visible nav and keep the hamburger/palette for secondary access.
- **Scope**: On desktop keep a persistent sidebar or top navigation.
- **Severity**: medium ; **Tags**: navigation, interaction-cost

## Web patterns: Interactions

### W2-81 Never hide primary actions behind hover  (src: hover-trap)
- **Rule**: Touch has no hover, so the first tap becomes a sticky hover that freezes revealed actions. Hover may surface extras only, and hover-only actions need a touch-reachable home (in the card, behind a swipe, or in a bottom sheet).
- **Why**: Touch users can't reach hover-only actions.
- **Do / Don't**: Do keep every primary action tappable. Don't hide primary actions behind hover.
- **Audit check**: grep `group-hover:opacity-100`, `:hover` reveal of buttons (`opacity-0 group-hover:`) for essential actions.
- **Restyle fix**: Make the actions always visible or move them into a menu/sheet on touch.
- **Severity**: high ; **Tags**: mobile, interaction-cost

### W2-82 Wrap hover styles in @media (hover: hover) and use pointer: coarse  (src: hover-trap)
- **Rule**: Test pointer capability with `@media (hover: hover)` instead of user-agent sniffing, and use `pointer: coarse` to enlarge controls for thumbs.
- **Why**: Mouse-equipped tablets keep full hover behavior while touch-only devices dodge sticky hover.
- **Do / Don't**: Do rely on media queries for hover and pointer. Don't infer touch from the user-agent string.
- **Audit check**: grep `navigator.userAgent` touch sniffing, `:hover` rules outside `@media (hover: hover)`, and `pointer: coarse` usage.
- **Restyle fix**: Wrap hover styles in `@media (hover: hover)` and add `pointer: coarse` sizing.
- **Severity**: medium ; **Tags**: mobile, interaction-cost

### W2-83 Pad touch targets to 44px while keeping icons about 20px  (src: hover-trap)
- **Rule**: A 20px icon looks fine in design review yet is hard to hit; pad the hit area to 44px while keeping the glyph small.
- **Why**: Undersized targets lead to taps landing in the wrong place.
- **Do / Don't**: Do expand the tap area to 44px. Don't let the icon's size set the target size.
- **Audit check**: grep icon buttons with `w-5 h-5`/`size-5` and no padding; computed button size under 44px.
- **Restyle fix**: Add padding (e.g. `p-3`) or `min-w-11 min-h-11` to icon buttons.
- **Scope**: 24px is the WCAG 2.2 AA minimum and a hard floor; 44px is the target (see the defaults table in the ux-doctor skill).
- **Severity**: medium ; **Tags**: mobile, accessibility

## Web patterns: AI-look tells

### W5-03 Keep motion for user actions, not a fade-up on every section  (src: frontend-design-skill)
- **Rule**: Motion the user did not trigger should be rare and should point at something; one orchestrated load or reveal works better than a fade-and-rise entrance on each section and a hover effect on every card, which is the generated default.
- **Why**: A single planned moment lands better than effects sprinkled everywhere, and a fade-up on each section is exactly what generated pages do by default.
- **Do / Don't**: Do animate responses to the user (open, expand, confirm) and at most one entrance moment per page. Don't attach the same scroll entrance to every section.
- **Audit check**: Count scroll-entrance hooks on section roots (`whileInView`, `data-aos`, `useInView`, `IntersectionObserver` + `opacity-0`/`translate-y-*`, `animate-*fade*`); flag 3 or more. Check that a `prefers-reduced-motion: reduce` path exists.
- **Restyle fix**: Remove the per-section entrances, keep one page-level moment if it carries meaning, and gate all non-essential motion behind `@media (prefers-reduced-motion: no-preference)`.
- **Scope**: Cascades of items that arrive from a user action or data load (W1-04) are fine, and so is scroll-driven motion for progress bars, sticky-header changes and one page-level moment.
- **Severity**: low ; **Tags**: motion

### W5-04 Never hide content behind a scroll-triggered entrance  (src: ai-design-slop-review)
- **Rule**: Content must be visible without its entrance animation: when a section starts transparent and waits for a scroll observer, a trigger that never fires leaves a blank section, which is a defect, not a matter of taste.
- **Why**: When the trigger does not fire, the reader gets an empty section instead of the content; likely causes include fast scrolls, anchor jumps, printing, reduced-motion settings and slow or blocked scripts (inference).
- **Do / Don't**: Do start content visible and add the animation as an enhancement. Don't ship sections whose resting style is `opacity: 0` until a script runs.
- **Audit check**: grep for elements that start hidden (`opacity-0`, `opacity: 0`, `initial={{ opacity: 0`) and only become visible through `whileInView`, `data-aos` or an observer; render with JavaScript disabled, with `prefers-reduced-motion: reduce`, and after jumping to an anchor further down, and check every section shows its content.
- **Restyle fix**: Make the visible state the default and apply the hidden start only when script and motion are allowed (e.g. a class set by JS inside `prefers-reduced-motion: no-preference`), or use a CSS view timeline whose resting state is visible (W3-52).
- **Severity**: high ; **Tags**: motion, states
