## Intro: UI + UX together (p.3-5)

### A-01 Don't ship a beautiful UI that doesn't help users finish the task  (p.3)
- **Rule**: A UI sets the tone within seconds; people stay or leave quickly. A polished visual layer (buttons, typography, graphics) is wasted if users struggle to complete basic tasks, get lost in navigation or can't find what they need. UI and UX are "two sides of the same coin"; you can't have one without the other.
- **Why**: Visual brilliance without usable flows goes to waste; the interface immediately sets the tone for the whole experience.
- **Do / Don't**: Bad example (thumbs-down): a flight-booking landing page ("Book your dream flight in just a few clicks!") with a gorgeous illustrated airplane hero, clean nav, but the only call to action is a single blue "Search flights" button. There is no way to enter From/To/Dates on the page, so the headline promise ("a few clicks") isn't supported by the UI (from visual).
- **Audit check**: Does the hero/landing promise a task (search, book, sign up) that the first screen lets the user start directly? Is the primary task reachable without extra navigation? Is there decorative imagery but no task-entry component?
- **Restyle fix**: Put the task's core input (e.g. search form) directly in the hero, keep the visual styling, and make the primary action live there.
- **Severity**: high ; **Tags**: [interaction-cost, hierarchy, craft]

### A-02 Don't ship good UX with an unpolished, bare UI  (p.4)
- **Rule**: Even with rigorous research (personas, documented needs, mapped flows), neglecting UI quality yields a product that feels outdated or unpleasing and may lose to more visually appealing competitors.
- **Why**: A functional, user-centred product still "might not stand a chance against more visually appealing competition".
- **Do / Don't**: Bad example (thumbs-down): same flight page, now with the full search form (Return/One way, Economy class, 1 passenger, 2 luggages; From Vienna VIE → To London STN; Departure Friday 17 June; Return Sunday 19 June; Search) but styled raw: no imagery, flat grey page, black square-cornered outline box and black rectangular "Search" and "Sign up" buttons, plain text, no icons, no elevation, small headline (from visual).
- **Audit check**: Is the form functional but visually flat – default black/grey buttons, hard 1px outlines, no brand colour, no depth, no iconography, no imagery?
- **Restyle fix**: Keep the flow, add visual polish: brand colour primary button with rounded corners, soft card elevation for the search panel, small accent icons for fields/dropdowns, supporting imagery.
- **Severity**: medium ; **Tags**: [craft, color, depth, buttons]

### A-03 Combine strong UX and strong UI so the product is intuitive and loved  (p.5)
- **Rule**: The magic happens when both are right: a product that looks good and is intuitive/user-friendly. UI principles are not only about making things pretty but about giving people a good experience.
- **Why**: Good aesthetics + good flow => intuitive, user-friendly, loved.
- **Do / Don't**: Good example (thumbs-up): same flight page with the illustrated airplane hero on the right and the search form placed as a floating, rounded, soft-shadowed white card overlapping the hero image; blue filled "Search" button (primary), small amber/orange accent icons on the passenger/luggage dropdowns, arrows between fields and radio dots; light-blue tinted top row for trip options; light-blue "Sign up" button in nav; active nav item has a dot (from visual).
- **Audit check**: Does the hero combine imagery + the task component? Is there one clear primary button, a card elevation separating the form from the background, and consistent accent colours/icons?
- **Restyle fix**: Elevate the form into a card (rounded corners, soft shadow), colour the primary CTA, add subtle accent icons to fields.
- **Severity**: medium ; **Tags**: [craft, hierarchy, depth, color]

## Visual hierarchy (p.7-12)

### A-05 Express importance through size, colour, weight and position  (p.7)
- **Rule**: Visual hierarchy = arranging elements to show relative importance and guide the eye, attention and actions, using size, colour, weight and position. If everything has the same size and colour, nothing stands out.
- **Why**: "You're basically shouting all the information at once, and nobody knows what to focus on."
- **Do / Don't**: Don't: shopping cart (Avocado $4.50, Lime $4.20, Orange $2.50, Total $11.20) where every button – three "Remove" buttons, "Continue shopping" and "Checkout" – is the identical dark-navy/purple filled rectangle, so all look equally important (thumbs-down).
- **Audit check**: Count filled/solid buttons with identical colour+size per decision group AND per viewport (the global header/nav is part of the first viewport, sticky or not; inference). More than one equal-weight primary-styled button in either, the same CTA (label + destination) filled twice in one viewport, or destructive row-level actions styled like primary CTAs = violation.
- **Restyle fix**: Assign one primary, one secondary, one tertiary style (see A-07/A-08) and demote repeated row actions.
- **Severity**: high ; **Tags**: [hierarchy, buttons]

### A-06 Colour-coding buttons alone doesn't create hierarchy  (p.8)
- **Rule**: Giving each button a different colour (red "Remove", blue "Continue shopping", green "Checkout") but keeping the same size and style still leaves users unsure which action matters most.
- **Why**: Colour differentiates but doesn't rank; all buttons keep equal visual weight.
- **Do / Don't**: Bad (thumbs-down, left): three red/pink filled "Remove" buttons (one per row), blue full-width "Continue shopping", green full-width "Checkout" – same size, same filled style, three competing colours.
- **Audit check**: Are multiple buttons different hues but the same fill/size/shape? Does a rainbow of solid button colours appear in one component?
- **Restyle fix**: Reduce to one saturated filled CTA; use neutral/ghost styles for the others (see A-07).
- **Severity**: high ; **Tags**: [hierarchy, buttons, color]

### A-07 Make one primary action vibrant, secondary muted, tertiary text-only  (p.8)
- **Rule**: "Checkout" = primary: vibrant green filled button, easy to spot. "Continue shopping" = secondary: same size as Checkout but grey (light grey fill, dark text) so it demands less attention. "Remove" = least prominent: only red/pink coloured text with underline, no filled background.
- **Why**: Clear action ranking tells users what to do next.
- **Do / Don't**: Good (thumbs-up, right): green filled Checkout, light-grey filled Continue shopping (same size), small underlined pink/red "Remove" text link under each item. Rows keep price at right; unchanged layout otherwise.
- **Audit check**: Per action group: exactly one filled saturated button; secondary buttons use neutral/grey/outline; per-row destructive/repeated actions are text links (small, underlined or coloured text), not filled buttons.
- **Restyle fix**: Primary = brand-coloured solid; secondary = neutral grey fill (same size is fine); tertiary/destructive-in-row = underlined text link in red.
- **Severity**: high ; **Tags**: [hierarchy, buttons, color]

### A-08 Don't let imagery overpower the key details  (p.9)
- **Rule**: Don't make decorative/supporting elements disproportionately large. In the cart, oversized product photos steal the spotlight from product name, price and quantity.
- **Why**: Upsets visual balance (principle covered later) and pulls the eye from important details.
- **Do / Don't**: Bad (thumbs-down, left): cart with very large round product thumbnails (≈ 70px in a ≈ 250px-wide card, from visual) dwarfing the text; name/price/remove small.
- **Audit check**: Is the image/thumbnail height larger than ~2-3x the line-height of the primary text block next to it, or does the thumbnail visually outweigh name+price? (threshold from visual, no numeric value given.)
- **Restyle fix**: Reduce thumbnail size (≈ 40px in the good variant, from visual) so text carries the row.
- **Severity**: medium ; **Tags**: [hierarchy, imagery, layout]

### A-09 Don't emphasise secondary information (e.g. quantity) over primary information  (p.9)
- **Rule**: Even when balanced, if less critical info (quantity "1 piece") is shown in larger font and higher contrast than product name or price, hierarchy is wrong. Quantity is useful but must not draw attention from what the product is and what it costs.
- **Why**: Attention goes to the least important data.
- **Do / Don't**: Bad (thumbs-down, right): small thumbnails, product name (Avocado/Lime/Orange) rendered light grey and small, "1 piece" rendered larger and darker than the name, price at right normal.
- **Audit check**: Compare font-size/colour of item name, price, and meta (quantity, SKU, date): is meta size >= name size or meta colour darker than name colour?
- **Restyle fix**: Name = darkest/medium weight; price = clear; meta (quantity) = smaller + lighter grey.
- **Severity**: medium ; **Tags**: [hierarchy, typography, contrast]

### A-10 Rank elements by user importance before designing  (p.10)
- **Rule**: Before touching the design, list all features/elements the UI must include and rank them by importance to the user; then use colour, size, position and contrast to highlight the key information and guide users.
- **Why**: Prevents emphasising the wrong elements ("a common mistake").
- **Do / Don't**: Process rule, no visual pair of its own.
- **Audit check**: For each screen, can you name the top 1-3 (inference) pieces of information/actions? Does the visual weight order match that ranking?
- **Restyle fix**: Make a ranked list; re-style so rank 1 gets the largest/darkest/most contrasted treatment, lower ranks recede.
- **Severity**: high ; **Tags**: [hierarchy, craft]

### A-11 In metric cards make the value bigger than the label  (p.10)
- **Rule**: In KPI/stat cards, the figures (e.g. $4,981.00, 591, 2,121, trend +3.2%) should be the most prominent text; the metric titles (Earnings, Sales, Views) should be small and secondary.
- **Why**: Users came for the numbers; large titles take focus away from the actual values.
- **Do / Don't**: Bad (thumbs-down, top row): dark cards with big bold titles "Earnings / Sales / Views" and tiny values ($4,981.00 with small green ↗3.2%, 591, 2121). Good (thumbs-up, bottom row): same dark cards with a small muted label above and a large bold value ("$4,981.00" with small green "↗ 3.2%", "591", "2,121" – thousands separator applied), sparkline at the bottom, small coloured icon dot top-right.
- **Audit check**: In stat/metric cards, font-size(value) > font-size(label)? Typical good ratio ≈ 2x+ (from visual). Are values formatted with thousand separators (2,121 vs 2121 in the bad version)?
- **Restyle fix**: Label: small (~12px), muted; value: large (~2x), bold, white/high-contrast; keep trend indicator small and coloured.
- **Severity**: high ; **Tags**: [hierarchy, typography, cards]

### A-12 Darker/stronger text for the title, lighter for supporting text  (p.11)
- **Rule**: Darker colours draw more attention and signal importance; lighter colours recede. Title should be dark black, supporting paragraph grey – not the reverse.
- **Why**: A grey title with black body undermines the title's importance.
- **Do / Don't**: Bad (thumbs-down, left card): title "Personal Injury Law" in grey, paragraph ("Attorneys in this field handle cases related to accidents, injuries, and wrongful deaths, seeking compensation for victims") in dark black. Good (right card): title in near-black, paragraph in mid-grey. Both cards have two small round icons (scales, gavel) on top.
- **Audit check**: Compare contrast ratio/lightness of heading vs body in the same block: heading contrast must be ≥ body contrast (heading colour darker than body on light themes; lighter on dark themes).
- **Restyle fix**: Heading → text-primary (near-black); body → text-secondary (grey, still accessible).
- **Severity**: high ; **Tags**: [hierarchy, contrast, color, typography]

### A-13 Use a vibrant colour to highlight the key action  (p.11)
- **Rule**: Making a clickable element a vibrant colour (e.g. a blue button) contrasts with surrounding text and naturally guides the eye, reinforcing its importance.
- **Why**: Colour contrast with the rest of the content attracts attention.
- **Do / Don't**: Text-only guidance (no pair shown on this page).
- **Audit check**: Is the primary button/link the most saturated element in its region? Does it differ in hue/saturation from the neutral text around it?
- **Restyle fix**: Apply a saturated brand colour to the primary action only; keep other text neutral.
- **Severity**: medium ; **Tags**: [hierarchy, color, buttons]

### A-14 Differentiate information by size, weight, colour and icons instead of uniform label:value lists  (p.12)
- **Rule**: Don't present all information with equal styling (label: value rows). Use font weight, size, colour and visual cues like icons to direct attention to what matters (price, title, status, key specs, contact).
- **Why**: A uniform list gives no hierarchy, so users can't scan or spot key info.
- **Do / Don't**: Bad (thumbs-down, left): property card with house photo and then 8 identical rows: "Type: For sale", "Price: £1,273,279", "Location", "Size: 1634 sqft", "Bedrooms: 5", "Bathrooms: 3", then "Contact person: Jennifer Bloom", "Phone number" – same size, bold labels in left column + values in a second column. Good (thumbs-up, right): big bold price "£3,273,279" at top-left; "For sale" shown as a small pill/badge at top-right (soft yellow); title "Luxury 5-bed Villa" in bold below; grey address with a location pin icon; a row with three icon + value specs ("1634 sqft", "5 bed.", "3 bath." with bold numbers, light units) separated by thin dividers; a footer with a small avatar, name "Jennifer Bloom" in bold, and phone in grey. (Note price differs between versions in the PDF: £1,273,279 vs £3,273,279.)
- **Audit check**: Detail cards/pages that list ≥5 (inference) key:value pairs with identical font-size/weight/colour for every row; labels like "Price:" "Type:" repeated. Missing icons/badges for status, unformatted key metrics.
- **Restyle fix**: Promote price to the largest, bold; turn status into a badge; group specs into one icon+value row with dividers; drop labels where icon/format makes meaning obvious; reduce contact info to avatar + name + phone.
- **Severity**: high ; **Tags**: [hierarchy, typography, icons, cards]

## Proximity (p.13)

### A-15 Group related items closely and separate unrelated ones (Law of Proximity)  (p.13)
- **Rule**: Elements close together are perceived as related; those far apart as separate (Gestalt Law of Proximity). Spacing between items must therefore encode grouping; equal spacing everywhere erases grouping.
- **Why**: Correct proximity significantly reduces cognitive load; equal gaps make users second-guess which label goes with which field.
- **Do / Don't**: Bad (thumbs-down, left form "Contact details"): the "Surname" label sits 28px below the "Name" field and 28px above its own "Surname" field – equal 28/28 spacing, ambiguous. Form fields: Name, Surname, Street address, City/Town, Occupation, Images (Browse).
- **Audit check**: For stacked label+input pairs, gap(label→its input) must be clearly smaller than gap(previous input→this label). Flag if the two gaps are equal or the ratio is < ~2:1 (inference) (the example is 12 vs 32 = ~2.7:1).
- **Restyle fix**: Reduce label→input gap and increase field-group gap (see A-16).
- **Severity**: high ; **Tags**: [spacing, forms, layout]

### A-16 Use ~12px label-to-field and ~32px field-to-next-label spacing  (p.13)
- **Rule**: Example of correct application: "Surname" label 12px from its own field and 32px from the "Name" field above.
- **Why**: Closer = related; makes it crystal clear which label belongs to which field.
- **Do / Don't**: Good (thumbs-up, right): label–field gap 12px, gap to the previous field 32px (annotated with magenta 32 / 12 tags); fields are light-grey filled rounded inputs.
- **Audit check**: Form CSS: label margin-bottom ≈ 12px (or 8-12 (inference)), field-group margin-bottom ≈ 32px; i.e. inter-group gap ≥ ~2.5x intra-group gap (inference).
- **Restyle fix**: Set label margin-bottom 12px; set group gap (field → next label) 32px (Tailwind e.g. `mb-3` label, `space-y-8` between groups).
- **Severity**: high ; **Tags**: [spacing, forms]

## Clarity (p.14-16)

### A-17 Clarity: make interaction understandable without confusion  (p.14)
- **Rule**: Clear interfaces let users understand how to interact without getting lost: straightforward navigation, intuitive layouts, easily readable text. A clear interface minimises time and mental effort. Three common mistakes undermine it: oversimplification, overwhelming complexity, misguided UX.
- **Why**: Lack of clarity makes tasks hard and elements' purposes unclear.
- **Do / Don't**: Intro; examples follow in A-18 to A-20.
- **Audit check**: Can a first-time user say what each control does and what happens next without guessing? Check the three failure modes below.
- **Restyle fix**: see A-18 to A-20.
- **Severity**: high ; **Tags**: [craft, interaction-cost, accessibility]

### A-18 Don't oversimplify: keep essential labels and context  (p.14)
- **Rule**: Over-simplified designs lack the context users need to know what to do next. Keep text labels with icons/toggles.
- **Why**: Simplicity taken too far backfires; users can't tell what each control does.
- **Do / Don't**: Bad (thumbs-down, left "Smart home settings"): three tiles each with only a coloured icon (shield, lamp, arrows) and an off-state toggle, no text. Good (thumbs-up, right): same three tiles with labels "Home security", "Lights", "Air conditioning" plus toggles shown in both states (green = on for Home security and Air conditioning, grey = off for Lights) and meaningful icons (shield, bulb, fan).
- **Audit check**: Icon-only controls (toggles, tiles, nav) with no visible label/aria-label/tooltip; toggles whose on/off state isn't visually distinguishable or labelled.
- **Restyle fix**: Add a visible text label under/next to each icon; use clear on/off colours (green on, grey off); choose self-explanatory icons.
- **Severity**: high ; **Tags**: [icons, accessibility, states, craft]

### A-19 Don't overwhelm: limit options, buttons and information  (p.15)
- **Rule**: Interfaces packed with excessive options, buttons and info increase cognitive load and make decisions and finding things harder, even if you think you're giving more control.
- **Why**: Over-complexity is as bad as over-simplification.
- **Do / Don't**: Bad (thumbs-down, left): dark mobile "Dashboard" with orange accents: hamburger, "16 Habits", "Get Premium" badge, gauge, three outlined stat boxes (Average Self Rating, Habits Active, Habits Completion), two big orange buttons (Add More Habits / Track Your Habits), "Recommended Habits" list with many orange "+" buttons (hydrate, Exercise, Sleep…, Get Outside), a 3-column category grid (Mood, Productivity, Health) with more "+" items, total score, weekly score bar, FAB "+" and bottom nav of 4 tabs (Routines, Track Habits, Dashboard, Rate Day); tiny text, outlines everywhere, single orange used for everything. Good (right): calendar week strip (December 2023, M–S with the selected day 18 highlighted in lime), one big ring "Burned calories 652 Cal", three small rings (Steps 6540, Time 45 min, Heart 72 bpm), "Finished workouts" list with check items, icon-only bottom nav with selected state; lime accent, lots of space.
- **Audit check**: Number of distinct interactive elements per screen (e.g. > ~7-10 competing actions, multiple stacked sections each with own CTA); duplicated accent colour on everything; small text. (No numeric threshold is given in the PDF.)
- **Restyle fix**: Cut to a focused set of key metrics/actions; use progressive disclosure; group via rings/cards; reserve accent colour for the active/selected state.
- **Severity**: high ; **Tags**: [hierarchy, layout, interaction-cost, craft]

### A-20 Don't mislead: make copy and control states say the same thing  (p.16)
- **Rule**: Even a balanced design fails clarity if the UX is incorrect or misleading: instructions and control states must agree.
- **Why**: Misleading UX makes users do the wrong action.
- **Do / Don't**: Bad (thumbs-down, left): list of Raspberries (checked), Mango, Pistachios (checked), Kiwi with title "Unselect items you want to remove" and green Save – the checked items would be the ones kept, which inverts the usual meaning and the checkbox semantic. Good (right): title "Select items you want to remove" with Mango and Kiwi checked, same Save button – checked = affected item, instruction matches the control behaviour.
- **Audit check**: Does the checkbox/toggle's checked state match the verb in the label/title (check = act on)? Do instructions use negated/inverse logic ("unselect to…")? Are default states pre-checked in a way that contradicts the instruction?
- **Restyle fix**: Rewrite the instruction to positive, direct form ("Select items you want to remove"); ensure checked = the thing that will happen; no default pre-checked contradiction.
- **Severity**: high ; **Tags**: [copy, forms, states, interaction-cost]

## Alignment (p.17-19)

### A-21 Align elements on shared axes for order and polish  (p.17)
- **Rule**: Alignment = arranging text, images and components along common lines/axes to create visual order and harmony. Poor alignment looks messy and is hard to use.
- **Why**: Gives a polished, organised look; misalignment hurts readability and perceived quality.
- **Do / Don't**: Intro to the following two examples (A-22, A-23).
- **Audit check**: Do left edges of titles, body text, buttons, icons within a component fall on the same x line (unless intentional hanging icon)? Check computed left offsets/padding.
- **Restyle fix**: Snap all items to common axes (see A-22 - A-28).
- **Severity**: medium ; **Tags**: [alignment, layout, craft]

### A-22 Don't misjudge alignment: icon, title, body and button should share a clean edge  (p.17)
- **Rule**: Alignment can be wrong by misjudgement: aligning things incorrectly (e.g. text indented next to an icon so the body and button no longer line up with the title).
- **Why**: Incorrect alignment creates a ragged, messy card.
- **Do / Don't**: Bad (thumbs-down, left card "Cactus"): title "Cactus" at left edge; below it a round cactus icon at the left edge with paragraph and "Learn more" pill button indented to the right of the icon, so the body/button don't align with the title. Good (right card): icon and title in one row at the top; paragraph and "Learn more" button below, both flush left on the same left edge as the icon.
- **Audit check**: In cards, does body/button left edge equal title/icon left edge? Is an icon floated alongside a multi-line paragraph, causing text indentation?
- **Restyle fix**: Put icon + title in a header row; place body text and button below on the card's common left edge.
- **Severity**: medium ; **Tags**: [alignment, cards, layout]

### A-23 Don't forget to align items: list items must share left/right edges  (p.18)
- **Rule**: Bad alignment also happens when you forget to align things properly; list items need identical edges.
- **Why**: Staggered edges look sloppy.
- **Do / Don't**: Bad (thumbs-down, dark "Resources" list with dashed guideline overlay): pill items "All", "Illustrations", "UI resources", "Icons" have different left/right edges and different offsets of icon and label (staggered by a few px, from visual). Good (right): all four pills share the same left and right edges, icons share an x-axis, labels share an x-axis.
- **Audit check**: Menu/list items: identical `x` and `width`, same icon column x, same label x. Compare bounding boxes in Figma/DOM.
- **Restyle fix**: Use one container with consistent padding and `flex-col` with `align-items: stretch`; same icon size & gap.
- **Severity**: medium ; **Tags**: [alignment, navigation, layout]

### A-24 Left-align most text, especially long text and lists  (p.18)
- **Rule**: Left alignment is the go-to for most text; it creates a clean left edge that's easy to read, especially for paragraphs and lists.
- **Why**: Clean, consistent starting edge speeds reading.
- **Do / Don't**: Text guidance only.
- **Audit check**: Paragraphs/lists with `text-align: center` or right (in LTR).
- **Restyle fix**: Set `text-align: left` (`text-left`) for body text and lists.
- **Severity**: medium ; **Tags**: [alignment, typography]

### A-25 Right-align numbers (and RTL languages)  (p.18)
- **Rule**: Right alignment suits numbers such as prices or table data because values line up from the right, making comparisons at a glance easier. It's also the correct alignment for RTL languages like Arabic.
- **Why**: Easier value comparison.
- **Do / Don't**: Text guidance only.
- **Audit check**: Numeric table columns left-aligned or centred; decimals/digits not lining up; use of `tabular-nums`? (the latter not mentioned; only right alignment).
- **Restyle fix**: `text-align: right` (`text-right`) on numeric columns (and their headers); RTL pages use right alignment.
- **Severity**: medium ; **Tags**: [alignment, tables, typography]

### A-26 Centre-align only short, standout items (titles, CTAs), never long text  (p.18)
- **Rule**: Centre alignment works for things that need to stand out, like titles or call-to-action buttons; avoid it for longer text blocks.
- **Why**: Starting point of each line changes, so eyes work harder to track the text.
- **Do / Don't**: Text guidance only.
- **Audit check**: Centre-aligned paragraphs with more than ~1-2 lines (threshold not specified in PDF).
- **Restyle fix**: Switch multi-line centred copy to left alignment; keep centring for headings and button labels.
- **Severity**: medium ; **Tags**: [alignment, typography]

### A-27 Use a layout grid to align elements consistently  (p.19)
- **Rule**: Implement a grid system to make aligning easier and keep consistency across different parts of the UI.
- **Why**: Grids give shared columns and gutters.
- **Do / Don't**: Example: Figma "Layout grid" overlay (pink FF17BE at 17% opacity columns) behind three cards ("Alignment", "Visual hierarchy", "Proximity"), each card sitting exactly in one column. Settings: Columns, Count: 3, Colour: FF17BE 17%, Type: Stretch, Width: Auto, Margin: 79, Gutter: 70.
- **Audit check**: Do element widths/left edges match a column+gutter grid? Are margins/gutters consistent across sections? Check for a defined container/grid (CSS grid, Tailwind `grid-cols-*`, Figma layout grid).
- **Restyle fix**: Define a column grid (count, margin, gutter) and snap components to columns.
- **Severity**: medium ; **Tags**: [alignment, layout, spacing]

### A-28 Use auto-layout so elements stay placed correctly  (p.19)
- **Rule**: Auto-layout ensures every element sits exactly where it should without manual nudging.
- **Why**: Avoids manual alignment errors.
- **Do / Don't**: Text guidance only.
- **Audit check**: Are positions set by absolute offsets/manual nudges (absolute positioning, manual margin hacks) instead of flex/grid/auto-layout and consistent gap?
- **Restyle fix**: Rebuild with Figma auto-layout / CSS flex/grid with consistent padding and gap tokens.
- **Severity**: low ; **Tags**: [alignment, layout, craft]
